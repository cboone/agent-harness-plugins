## Summary

Repoints every `cboone/gh-actions` reference in the plugin templates from v3.0.0 (and the two scaffold-zig-cli refs at v3.1.1) to v4.1.0, bumps this repository's own CI alongside them, and adds notes where v4 changes what a scaffolded repository sees on its first CI run. Closes #399 and folds in both extra findings from #383. 45 references across 26 canonical files in 14 plugins, with the Codex mirror regenerated.

The upgrade crosses a major release, and the branch does the work that distinction demands: every template was checked against the v4 migration guide's affected-inputs table rather than having its hash swapped blind. That check was correct and is the strongest part of the branch. The documentation half is where it falls short: it covers three consumer-visible behavior changes and misses two, one of which flips a secret-scanning job from passing to failing.

## Code Quality Assessment

**Overall: not ready to merge.** The mechanical work is accurate and well verified, and I could not find a defect in the 45 repointed references. But the branch's own stated purpose includes documenting what v4 changes for scaffolded repositories, and it documents three of five. One omission is significant enough to change whether a scaffolded repository's CI passes.

### Strengths

- **The migration check is the right depth.** Cross-referencing every template against the affected-inputs table, and recording in the commit message which inputs were checked and why each is safe, is what a major-version bump warrants. The two `targets` values were reasoned about specifically rather than waved through.
- **The substitution was defended, not just performed.** Keying on SHA plus version comment, and asserting bare-SHA and paired-SHA counts match before rewriting, means a drifted or unpaired occurrence would have failed loudly. The placeholder and token survived by construction, not by luck.
- **A false claim was found and fixed.** The `scaffold-zig-cli` note asserting the format job skips `build.zig.zon` became wrong at v4 and was rewritten. Catching a note that silently inverted is more valuable than the pin refresh itself.
- **`jq` reflow was caught and reverted.** Bumping versions with `jq` reformatted the `keywords` arrays; running Prettier restored them, and the manifest diffs were then verified to be version-only. Worth noting the tool choice caused it: `jq` does not preserve formatting and a targeted `sed` would have avoided the round trip.
- **Claims were verified rather than asserted.** The `make lint-shell` check before bumping `ci.yml`, the confirmation that v4.1.0 still calls the same five Makefile targets, and the check that the Zig Makefile covers `build.zig.zon` are each load-bearing and each was actually run.

### Issues to address

#### 1. TruffleHog now fails scans that previously passed, and nothing says so. (High)

`plugins/set-up-secret-scanning/skills/set-up-secret-scanning/references/trufflehog-workflow.md` moves to v4.1.0 with no note. At v4, `run-trufflehog` invokes:

```text
trufflehog "${args[@]}" --no-update --results=verified,unknown --fail
```

`--fail` was not passed at v3.0.0. The v4.0.0 notes state it plainly: "a scan reporting a verified or unknown result exits 183 instead of succeeding." So a repository scaffolded from this skill had a secret-scanning job that could report findings and still go green, and after this branch it goes red.

This is the most consequential behavior change in the whole upgrade. It is also a fix rather than a regression, which is exactly why it deserves a note: a maintainer seeing their scan fail for the first time needs to know it is the pin move and that the previous green was not trustworthy. v4 also adds a `trufflehog-allowlist` input for reviewed findings, which is directly relevant to a skill that has to cope with deliberate credential-shaped fixtures, and is worth mentioning in the same note. The file already has a Notes section to put it in.

#### 2. golangci-lint moves 2.11.4 to 2.13.2 for every Go template. (Medium)

`run-go-ci.yml`'s `run-lint` defaults to true and its `golangci-lint-version` default moved from 2.11.4 to 2.13.2. Several templates set `run-lint: true` explicitly: `scaffold-go-cli/references/ci-workflow.md`, `scaffold-go-library/references/ci-workflow.md`, `set-up-ci/references/ci-go-library.md`, `set-up-linters/references/tools/github-actions-ci.md`.

This is the same class of change as the ShellCheck 0.9.0 to 0.11.0 jump, which did get a note. Treating one and not the other is inconsistent, and a new golangci-lint minor can surface findings on a first run just as a new ShellCheck can.

#### 3. The plan file is committed in the same commit as the work. (Low)

Not wrong under this repository's convention, which retains plans in `cboone` repos, but it means the plan and the deviations from it land together, so the plan reads as a post-hoc description rather than a prior specification. Worth being aware of when reading the history.

### Checked and deliberately not flagged

Two further v4 tool bumps look like they belong on the list above and do not, because they are unreachable from these templates:

- **cargo-deny 0.19.4 to 0.20.2**, explicitly called out upstream as behaviorally breaking. `run-deny` defaults to `false` and no template sets it.
- **`crate-ci/typos` dictionary updates**, which upstream warns "may flag words that previously passed". `run-typos` defaults to `false` and no template sets it.

Both were verified against the v4.1.0 workflow source rather than assumed.

### Suggestions

- **`run-scrut-tests.yml` gained `setup-uv` and `uv-version` in v3.2.0.** `add-scrut-cli-tests` currently leaves runtime installation to a hand-rolled `scrut-setup-cmd`. The new inputs remove that need for a CLI shipped as PEP 723 scripts. Not a breaking change and out of scope here, but the skill is now a release behind a capability that was added for its use case.
- **`lint-text.yml` gained `cspell-config`, `cspell-files` and `extra-cspell-packages`.** `set-up-linters` calls `lint-text.yml` and could expose them. Again additive, and reasonably left for its own change.
- **Consider a `sed`-based version bump next time** rather than `jq`, to avoid the reformat-and-restore round trip on the manifests.

## Recommendation

Add the two missing notes, then merge. Both are additions to Notes sections in files the branch already touches, and neither changes any template's behavior. `set-up-secret-scanning` and the four Go template files would need patch bumps if their current bumps are already consumed by this commit, and `dist/` regenerated.

The underlying lesson is worth recording separately: the v4 behavior-change list belongs in the skills' own reference material or in a checklist, not re-derived by hand from release notes each time a pin moves. That is adjacent to #513, which asks whether these pins should be refreshed structurally rather than manually.

# Edit mode

Run this workflow only for explicit `--edit`. The calling session owns fixes; the initial and final reviewers receive no `--edit` and keep the report-only workflow, exclusions, JSON contract and read-only sandbox. Never change a report-only run to a writable Codex run. `--no-codex` selects the usual fallback; it grants no additional authority.

## Authority and preparation

`--edit` authorizes supported local source fixes, not staging, commits, stashes, checkouts, remote writes, dependency installation, credentials, live configuration or deployed services. Project gates still apply. `--run-checks` is still required for executing repository code, including tests, generators and formatters. It does not override project restrictions. If a project requires a commit or another gated action, return that requirement to the caller rather than doing it as part of this mode.

First require the clean-worktree precondition helper from the skill to pass. Staged, unstaged or untracked changes outside ignored files refuse the run before review or edits, with `failure` and `complete: false`. Tell the caller to commit or stash first, but do neither. The helper also refuses tracked-file flags other than ordinary `H` entries, including assume-unchanged and skip-worktree: status cannot establish cleanliness for those files. It also refuses every gitlink, registered or embedded and initialized or not, naming the path. Nested-repository cleanliness cannot be established by a parent status or flag inventory. Report the diagnostic without changing index flags or initializing a checkout. This applies even to changes outside `--files` or an explicit `--range`. Report-only mode keeps its existing behavior.

Load `review-until-clean` only to locate its bundled `review-scope` helper as its helper section describes. Do not start its loop. If the dependency or helper is unavailable, stop with `unavailable` before editing. Reuse its snapshot and tree capture. For edit-mode capture, resolve the default-branch ref using step 1's lookup, even with an explicit `--range`. Pass that ref as the helper's `--base`. This edit-only lookup does not replace the selected review range or change report-only range behavior. If no capture base can be resolved, stop before editing.

Keep all captures, reports and fix notes in a recorded temporary directory outside the repository, with `TMPDIR` checked as in `./codex-exec.md`. Preserve them until the report is delivered. Never put a ledger in the scope being reviewed. Record the original arguments, resolved scope, exclusions, HEAD and clean index state. Symlinks are link text only, never follow their targets. A local edit appearing after the precondition check invalidates the run; it is never permission to discard it.

## One bounded fix pass

1. **Capture and review.** Recheck the clean-worktree precondition after capture-base resolution. Run `review-scope --base <resolved-ref>` and preserve its JSON as `before.json`. Immediately recheck the precondition after capture, and require full committed coverage and empty staged, unstaged and untracked buckets in `before.json`. Stop on any failure before starting a reviewer. Run the normal report-only workflow with the user's arguments minus `--edit`. Preserve its exact JSON and plain-text report as the **initial review**. For checks requested by `--run-checks`, the ordinary fallback and mechanical-check rules still apply. Recapture the scope immediately afterwards and require the same `snapshot`; a check that moved it invalidates the review. A failed, unavailable, incomplete or no-op initial review ends the edit workflow without fixes. Keep its result, never replace it with an empty successful review.
1. **Decide every finding.** Number the initial findings and preserve their labels, evidence and initial locations. Fix only findings at or above `--severity`: `important` fixes Important; `nit` fixes Important and Nit, the default. A supported fix has a concrete local correction, an understood behavioral effect and a validation path. Search for all sites of the same mechanism before editing. Scope includes selected files and only necessary sibling sites, callers, tests and documentation in this repository. For each additional path, record why the same finding requires it. A `--files` filter is not permission for unrelated cleanup. Preserve generated-file, lock-file and vendored exclusions; change canonical sources and regenerate only through authorized project commands. If the full class cannot be fixed within these boundaries, leave it unresolved rather than applying a knowingly partial correction.
1. **Fix in the calling session.** Recheck the captured snapshot immediately before the first edit, and reread each site's captured contents before replacing it. Stop on unexpected content, index, HEAD or base movement; do not revert edits of uncertain origin. Stop to preserve concurrent staged, unstaged or untracked work; never revert it. Do not edit symlink targets or initialize or edit nested repositories; findings requiring those operations are unsupported and unresolved. Apply the supported fixes once, including necessary tests and docs. Record changed paths against each finding. An unsafe, ambiguous, blocked or unsupported fix is **unresolved**, with its reason and next action. Mark a finding **declined** only with evidence that no correction is warranted or an explicit caller decision; a difficulty applying it is not a decline. Do not invent user decisions or downgrade severity to avoid a fix.
1. **Validate.** Run relevant supported checks, with commands and results recorded separately. Repository code still requires `--run-checks` and project authorization. Without those, run available standalone read-only checks and list required repository checks as **unverified**, with exact commands. Use scoped checks and formatters so unrelated files do not change. Recheck actual disk changes after checks or generation, including unexpected and ignored outputs. A failed required check makes the aggregate `failure`; an unrun required check makes it incomplete and unverified. Keep edits for inspection; never discard them to make validation pass.
1. **Measure and review the fixes.** Capture `after.json` with the same helper and base. Require unchanged HEAD, base and index and account for every changed path and any unexpected movement. Compare the helper's before and after content trees with the hardened Git diff form from step 1 of the skill; compare raw trees too, since Git normalization can hide byte changes. Include additions, deletions, renames as old and new paths, and necessary siblings, even when excluded by the original `--files`. Check that remaining paths retain their captured contents. Unexpected changes invalidate the result; stop and report without reverting them.

   When changes exist, give a fresh report-only reviewer the measured before-to-after patches, the literal changed-path manifest, and the initial review as data. Its scope is this **captured fix diff**, not the user's original committed `--range`, which cannot include these uncommitted fixes. Explicitly replace workflow step 1's normal range collection with those captured inputs; review the final full contents of every changed non-generated file, examine siblings and walk the same checklist. Review added files directly and deleted files from the capture. Generated outputs remain excluded and are named in the report. Keep `--severity`, `--run-checks` and `--no-codex`; omit the original `--range`, `--files` and `--edit`. This is an internal supplied scope, not a new public option. A Codex reviewer still uses `--sandbox read-only` and the existing schema and completion checks. Resolve any PR body read in the calling session as usual. Recapture after the final review and require the same snapshot. Missing raw capture, unreadable changed files, an incomplete final review or unexplained movement prevents a clean result.

   If nothing changed, retain the initial review as the final review only while its snapshot is still valid. Do not run a duplicate review. Report new findings in the final review; do not fix them in another pass. This workflow ends here.

## Result

Return exactly one aggregate step 7 JSON in the existing shape, followed by a plain-text report. Do not add keys to `result-schema.json`. The report has separately labelled **Initial review**, **Dispositions**, **Validation**, **Final review** and **Scope and captures** sections, including capture paths and before and after snapshot identifiers. Preserve each phase's exact JSON in the captures; include initial finding text and final findings in the report so it stands alone. When a scripted caller uses the schema's `report` field, put this whole report there.

- The aggregate `reviewed` describes the original selected scope and the captured fix diff, naming necessary sibling additions. A fix-only final pass must not claim that it re-reviewed the entire original branch.
- The aggregate `findings` contains final-review findings plus all initial findings not verified fixed, deduplicated by mechanism and site. Keep declined items visible and identify their disposition in `detail`. Use current anchors where known; label historical anchors explicitly when edits displaced them. **Fixed** means the correction was validated and the final review verified it. An attempted fix with missing validation or verification remains unresolved and unverified. Keep original labels and evidence separately in the report.
- Union `not_reviewed`, `excluded` and `unverified` from both phases and validation, with phase names and reasons. Never erase an initial gap because the narrower final review did not encounter it. `complete` is true only when both required reviews completed, required validation passed and the captures remained valid. An edit run with required validation unverified is incomplete even if reading found no defects.
- `status` retains its existing meaning: `success` means reviews ran, not that all findings were fixed; `no-op` means empty initial scope; a failed required check, invalid capture or failed review yields `failure`; a missing required capability yields `unavailable`. All non-success statuses have `complete: false`. An unrun check can yield `success` with `complete: false`, never clean.
- Report counts and reasons separately for **fixed**, **declined**, **unresolved** and **unverified**. Clean requires `success`, `complete: true`, no outstanding findings at the selected threshold and no required unverified validation. A decline never silently turns into a clean result.

For repeated rounds use `review-until-clean` with this skill as a report-only reviewer, without `--edit`. That loop owns its fixer, snapshots, severity and ledger; this mode does not invoke it or reproduce its round policy. Existing report-only callers, including the Copilot resolver, retain their behavior.
